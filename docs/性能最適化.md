# 複数タブの性能最適化

2026-09-05。優先順位は、複数のMarkdownを開いたときの応答性、CPU/GPU負荷、メインメモリ消費量の順。応答性のためにRAMバッファを使用する指定に基づく。

## 実装

| 対象 | 変更 |
| --- | --- |
| タブ切替 | 最近使用した本文を同期表示し、更新確認だけをワーカースレッドで実行。スタンプ一致時のファイル読込・文字コード変換・ハッシュ計算を省略 |
| Markdown・Mermaid | 本文、解析済みブロック、図、文字配置、検索結果を再利用。本文・表示モード・フォント・幅・DPIの変化を判定 |
| スクロール | 読書位置の復元とアンカー移動を、本文全体のレイアウト更新から分離。高さだけの変更でも文字配置を再計算しない |
| 描画 | 同サイズの画面バッファを再利用。表示範囲のブロックを二分探索し、本文・コードの画面外の行は描画ループを省略 |
| SIMD | UTF-8のASCII部分をSSE2で16バイトずつ走査。非ASCIIはWindowsの厳密検証を使用し、64 KiBごとにキャンセル確認 |
| 読込バッファ | 最終文字列の領域へ直接ReadFile。UTF-16/CP932変換時は不要になった入力バッファを先に解放 |
| 更新・例外 | F5はスタンプが同じでも強制読込。読込失敗時は表示を保持。古いタブ・キャンセルされた要求の結果を破棄 |

本文キャッシュは8件・32 MiB。描画データキャッシュは非表示の最近使用した文書8件・64 MiBで、画像のラスターバッファも計上する。上限を先取りして確保せず、必要に応じて増やす。大きな画像で上限を超える場合は画像バッファを解放して本文のキャッシュを優先する。

容量は文字列・コンテナのcapacity、図の保持領域、画像の画素領域などの見積もり。アロケーター管理情報やGDI+内部領域は含まない。表示中の文書、ワーカーの処理中データ、画面バッファ、OSの領域は別に必要なため、合計96 MiBをプロセス全体のメモリ上限とはしない。閉じた文書の描画データも最近使用したキャッシュには残り得る。

## 同一条件での変更前後比較

Windows x64 Release / MSVC 14.51、CPU識別子 `Intel64 Family 6 Model 183 Stepping 1`。約1 MiBの日本語・ASCII混在本文を2文書用意し、980×720の非表示ネイティブビューで32回タブ切替、64回通常スクロールを実行。変更前後を交互に3プロセスずつ測り、各指標の中央値を採用した。測定中にC++ビルドは実行していない。

## GPUの判断

今回は独自のGPU処理を追加せず、GDI+描画を維持した。GPUには文字や図の描画を高速化し、CPU負荷を下げる用途がある。[MicrosoftのDirect2D API解説](https://learn.microsoft.com/en-us/windows/win32/direct2d/the-direct2d-api) にもGPUを使う文字描画の効果が説明されている。

ただし今回特定したタブ切替時のファイル再読込・解析・レイアウトの重複は、描画APIのGPU化では解消しないため、先にその重複を取り除いた。大量の図・画像のスクロール描画が支配的になった場合にDirect2D/DirectWriteへの変更を比較検討できる。GPU使用率・消費電力は今回測定しておらず、減少したとは評価しない。

## 2回目の最適化: 監視・ツリー・起動・図（2026-09-05）

メモリリークの静的レビュー（リークは見つからず）で挙げた効率面の指摘を修正した。優先したのは、大きなフォルダを登録したままファイルが大量に変化する状況でのUIスレッド負荷。

| 対象 | 変更 |
| --- | --- |
| 非Markdownの作成・削除・改名通知 | 通知ごとにTreeView全項目を `WalkItems` で走査していた判定を、モデルから作る既知フォルダ集合 `knownFolders` の検索に置き換え。ネイティブコントロールへの `SendMessage` は発生しない |
| 変更後の再走査 | 1件の変更で登録フォルダ全件を再走査していたものを、変更パスを含む登録フォルダだけに限定（`MarkTreeDirty` / `MarkWatchDirty`）。F5と起動時は従来どおり全件 |
| 再走査結果の反映 | 走査結果が現在の木と同一（`FolderNode::operator==`）なら TreeView を再構築せず、ルートの表題だけ更新。リネーム保存するエディタでの保存や30秒間隔の再確認で、項目の全削除・全挿入が消える |
| 監視バッファ | `ReadDirectoryChangesW` のバッファを4 KiBから64 KiBへ。ビルド出力のような一括変更でオーバーフローによる全再走査に落ちにくい。`ERROR_INVALID_PARAMETER` を返す共有では4 KiBへ戻して再試行 |
| タブ帯の描画 | 表示名の重複判定を `RebuildTabs` で数えた集計に変更し、可視範囲の項目だけ描画。以前はタブ数の二乗回の `fs::path` 生成が毎回発生していた |
| 起動時の復元 | `session.ini` をキーごとに `GetPrivateProfile*` で再解析していたものを、1回だけ読む `SessionFile` に置き換え。BOM判定（FF FE → UTF-16LE、他はANSI）、大文字小文字無視、最初のセクション・最初のキー優先、値の空白除去と引用符除去、空の値は整数では既定値、など実際のWindowsの結果と突き合わせる試験を追加 |
| 自動保存 | スクロール停止700 ms後の自動保存では `FlushFileBuffers` を省略。終了時と明示保存は従来どおり同期フラッシュ |
| Mermaid | `std::regex` を呼び出しごとに構築していた3箇所を静的化。文字幅計測の Bitmap / Graphics / Font を1回の解析・描画で共有し、描画時の Font をサイズ・スタイル別にキャッシュ |
| 本文検索 | 検索欄の1文字入力ごとに本文全体を小文字化コピーしていたものを、本文が変わるまで再利用（検索を閉じると解放） |
| 選択 | マウス選択の当たり判定を y 座標近傍のブロックに限定。判定結果は全走査と厳密に同一で、実装時に3文書・数千点で新旧一致を確認してから旧実装を削除 |
| その他 | SHA-256 プロバイダをプロセスで1回だけ開く。`Tab::modified` / `Tab::size` の未使用フィールドを削除。ワーカーの catch 内で UTF-8 変換に失敗しても例外を投げない `ErrorText` |

見送った項目: 本文テキストの多重保持（piece のオフセット参照化）はレイアウト・選択・検索の全経路に波及するため別作業とする。BOM除去の memmove は10 MiBでも約1 msで、これ以上安い方法がない。

### 実測

同じPC（Intel64 Family 6 Model 183）で、他のアプリケーションが動作中の状態での測定。絶対値は負荷で変わるため、同一条件内の比較として読む。

| 指標 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 11,355項目の先頭フォルダ（9,781行）を同一内容で再走査した結果の反映 | 970.596 ms〜1,700 ms（全削除・全挿入） | 4.6 ms〜5.5 ms（挿入・削除 0件） |
| 32 / 100 / 256 タブの `App::Restore` | 16 / 78 / 266 ms | いずれも 1 ms 未満（`lifetime_probe` の `restore_ms` = 0） |

同一内容の再走査反映は `host_tests --tree-scroll-regression` の `deep-tree: identical 9781-row rescan accepted in ... ms` として毎回出力する。負荷の高い時間帯には同じ測定が210 msになったこともあり、この値はUIスレッドの処理量ではなく当日の負荷を示す。

副次的な観測として、テスト実行中にこのPCで動いていた旧ビルドの `dist\MMViewer.exe`（`C:\git\MMviewer` を登録済み）が、テストが生成するフィクスチャの変更通知に反応して約21分のCPU時間を消費していた。旧コードの全走査・全再走査が、実際の開発フォルダで再現した例である。

### 回帰試験

- `host_tests` に `TreeRescanEfficiencyChecks` を追加: 同一内容の再走査で `TVM_INSERTITEM` / `TVM_DELETEITEM` が0件でモデルと項目ハンドルが不変、片方のルートの変更で他方の世代番号が進まない、非Markdownファイル作成の通知処理で `TVM_GETITEM` が0件、監視バッファを8バイトに縮めた実際のオーバーフロー（回数を計上）からの回復、同名ファイルのタブ表題。
- `host_tests` に `SessionParserChecks` を追加: ANSI と UTF-16 の設定ファイルについて、引用符・空白・末尾の非数字・負数・`0x`・`4294967295`・空の値・重複キー・重複セクション・閉じ括弧のないセクション名を `GetPrivateProfileStringW` / `GetPrivateProfileIntW` / `GetPrivateProfileSectionNamesW` と突き合わせる。
- `viewer_tests` に本文長が同じ別文書での検索更新と、ドラッグ選択の端点（`SelectedText`）を追加。`diagram_tests` に1,500行の sequence と300ノードの flowchart の解析・再現性を追加。
- `host_tree_scroll` の CTest タイムアウトを120秒から300秒へ。空きマシンで約100秒、負荷時に2倍になるため。ハングの検出という目的は維持する。

## 3回目の最適化: フォルダ一覧の差分・分割適用（2026-09-06）

### 症状と原因

新ビルドで「応答なし」が出た。実測すると、登録フォルダ `C:\git\MMviewer` 配下に .md を1つ作る／消すだけで UI スレッドが10秒以上止まり、CPU 時間は2回で約22秒増えた。この root はテストが `artifacts\` に残した run-* フィクスチャ（11,123 .md）で17,026項目に膨らんでいた。

`tree_probe`（`tests/tree_probe.cpp`）でネイティブ TreeView の操作コストを測ると、挿入は約43 µs/項目だが削除は240〜650 µs/項目で、`DeleteAllItems` と `DestroyWindow` も17k項目で6〜12秒かかった。UI スレッドの命令位置を1 msごとに採取すると時間の79%が `NtUserNotifyWinEvent` で、comctl32 が項目1件ごとに発行するアクセシビリティ通知を、このPCで動く別アプリのフック先が受け取るために高価だった。ツリーを非表示にしても消えず、環境が詰まるほど1件あたりの時間が伸びる。走査結果が変わるたびに `ReplaceFolderTree` が root 配下を全削除・全挿入していたため、項目数×通知コストがそのまま停止時間になっていた。

| 操作（変更前、17,026項目） | 実測 |
| --- | ---: |
| 初回挿入 | 0.9〜1.0 秒 |
| 既存の木の入れ替え（.md を1件追加） | 14.4 秒（削除 3.8 秒＋再挿入 10.0 秒） |
| 先頭表示行を含む部分木を消した後の再挿入 | 削除前の10倍以上に悪化 |

### 変更

| 対象 | 変更 |
| --- | --- |
| モデル | `FolderNode::children` を `std::list` に変更。挿入・削除・`splice` で他ノードのアドレスが動かないため、TreeView 行の lParam（ノードへのポインタ）を付け替えずに済む。並び順の比較器 `FolderNodeBefore` を `core.h` で公開し走査と差分で共有 |
| 差分適用 | `ReplaceFolderTree` は旧モデルと新モデルを兄弟順にマージし、一致した部分木（`operator==`）は触れず、消えた項目は行を削除、増えた項目は行を追加する。モデルの変更はこのマージだけが行い、除外の反映は「除外を適用したコピー」との差分で行う |
| 分割実行 | 行の追加・削除を `TreeTask` としてキューに積み、`WM_TIMER`（10 ms）で **1回25 ms** ずつ実行する。挿入は再開可能な深さ優先で、フォルダは子を入れ終えてから1回だけ展開する。削除は子孫を先に集めて逆順に消す。小さな差分（挿入 ≤200 行・削除 ≤30 行）は同期で即反映 |
| 先頭表示行の保護 | 先頭表示行や選択行を含む部分木を消す前に、その部分木を折りたたみ、表示位置と選択を外へ移す（消した後の挿入が全項目走査になる現象を防ぐ） |
| 登録の退役 | 「リストから削除」した登録は、行の削除が終わるまで `retiringFolders` に保持する。行と登録の対応はパスではなくノードのポインタで判定し、同じパスの削除→再登録を混同しない |
| 保留 | 行の更新中に届いた新しい走査結果は登録ごとに最新1件を保留し、キューが空になった時点で差分適用する |
| 終了 | 製品の `WM_CLOSE` はウィンドウを隠して `PostQuitMessage` し、`DestroyWindow` を呼ばない（17k 行の破棄で数秒待たない）。終了中のウィンドウには `MMViewer.Closing` プロパティを付け、2重起動の検出から除外する。テストの `Host` は従来どおり `DestroyWindow` |
| すべて展開／折りたたみ | 同じキューで分割実行（展開は深い順、折りたたみは浅い順） |
| テスト出力 | 各スイートは起動時に自分の `run-*` を新しい2件だけ残して削除する（`PruneOldRuns`） |

## 4回目の最適化: 残りの同期処理と走査・通知・描画（2026-09-06）

### きっかけ

別セッションのエージェントによる評価（4件）と、3回目の後に行った調査を突き合わせた。

1. 既存フォルダ直下に .md を大量追加すると、`MergeTree` が兄弟行を同期で挿入していた（3回目はキューに渡すのが「子を持つフォルダ」だけだった）。
2. タブ切替の `SelectTreeFile` がツリー全行を `WalkItems` で走査していた。
3. 長い表は全文字片、図は全要素を毎回描画していた。
4. 非 Markdown の作成・削除・改名の通知ごとに UI スレッドで `GetFileAttributesW`（実測 50〜60 µs）を呼んでいた。

調査で分かっていたこと: `C:\git\VagWork\Vag` は表示 241 項目に対して全体走査が 12.7〜13.7 秒（73,906 ディレクトリ）。`RefreshFolder` が要求のたびに実行中の走査をキャンセルして作り直すため、ビルド中は長い走査が完了しない。走査ワーカーが1本で、起動時に遅い root が後続を待たせる。`EnumerateFolder` がディレクトリごとに親の列挙で分かっている属性を `GetFileAttributesW` で確認し直し、全エントリで `std::filesystem::path` を生成する。描画では `HitLink` の全ブロック走査、英単語の幅計測の未キャッシュ、ズームでのキャッシュ全消去、`HighlightCode` の割り当て、リサイズ中の全再レイアウト、監視 0 件でも動く 300 ms タイマー。

### 変更

| 対象 | 変更 |
| --- | --- |
| 兄弟行の追加 | `MergeTree` は新規ノードの連続区間（一致ノードの間）ごとに Insert タスクを1件積む。タスクの先頭フレームは親ノードの `[first, stop)` を走り（`Frame::stop`）、既存の再開可能 DFS をそのまま使う。200 行を超える区間は開始時に親行を折りたたみ、終了時に戻す |
| 兄弟行の削除 | 連続する消えたノードも1件の Delete タスクにまとめ（`EnqueueDeleteRun`）、30 行を超えるなら親行を折りたたんでから消す。開いた親の下で1行ずつ消すと行ごとに可視行が再計算されるため |
| パス→行の索引 | `rowsByPath`（大文字小文字を無視するハッシュと比較）。`InsertRow` でファイル行を登録し、`TVN_DELETEITEM` で「その行を指しているときだけ」解除する（同パスの再登録で退役行と新しい行が併存しても外れない）。`SelectTreeFile` は索引で引き、root 内なのに外れたときだけ従来の走査に戻る |
| 通知 | `MODIFIED` かつ非 Markdown はパスを組み立てる前に読み飛ばす。`REMOVED` / `RENAMED_OLD_NAME` は `knownFolders` だけで判定し、属性を取らない。`ADDED` / `RENAMED_NEW_NAME` の属性確認は残す（同一ボリューム内の移動は REMOVED + ADDED で通知され中身のファイルは通知されない）が、その監視を含む登録がすべて再走査待ちの間は省く。パスの連結は文字列結合、拡張子判定は末尾比較 |
| 走査の再要求 | 走査中（キュー待ちを含む）の要求は `rescanRequested` に合流し、キャンセルも世代更新もしない。結果を反映した後に1回だけ再走査する。`CancelFolderScans` は従来どおり全取消。結果の `PostMessageW` に失敗したら短い間隔で再試行する（失われた結果で `scanning` が立ったままになるのを防ぐ） |
| 走査の並列化 | ワーカーを固定プール `scanners[4]` にし、要求ごとに待ち件数（`Worker::Pending`）が最少のワーカーへ積む。終了・取消は全ワーカーに対して行う |
| `EnumerateFolder` | 親の列挙結果（ディレクトリ・再解析ポイント）を信頼し、ディレクトリごとの `GetFileAttributesW` を省く。消えていた場合は列挙が「見つからない」以外のエラーで失敗し、従来どおり `Uncertain` になる。子パスは `JoinPath` で連結（末尾が区切りなら足さない）、`.md` 判定は末尾比較（名前が拡張子だけの `.md` は従来どおり対象外） |
| 表 | レイアウト時に行ごとの文字片の開始添字 `rowPieceStarts` を記録し、描画は `rowEdges` の二分探索で表示範囲の行だけ描く |
| 図 | `DrawDiagram` は変換後の `GetVisibleClipBounds` を可視矩形とし、ノード・グループ・辺（端点＋制御点＋ラベルの包）・参加者・生存線・ブロック・活性化・イベントのうち矩形と交わらないものを描かない。境界は余裕を持たせ、部分的に見える要素は必ず描く |
| 描画の小改善 | `HitLink` を `lower_bound` で対象ブロックに限定。16 文字以下の語の幅を完全一致キー（文字列・サイズ・スタイル）でキャッシュ。ズームと DPI 変更で `fonts` / 幅キャッシュを消さない（キーにサイズを 0.01 px 単位で含む。`fonts` は 64 件で全消去、幅は 32,768 件で全消去して再開）。`HighlightCode` はキーワードを `unordered_set` で引き、語の小文字化はスタック上で行う |
| ライブリサイズ | メインウィンドウの `WM_ENTERSIZEMOVE` / `WM_EXITSIZEMOVE` で `SetLiveResize` を呼び、ドラッグ中は幅の変化による再レイアウトを保留して旧レイアウトを描く。終了時に1回だけ再レイアウト。初回レイアウトと DPI 変更は保留しない |
| 監視タイマー | 監視 0 件のときは完了ポーリング（タイマー 1、300 ms）を止め、監視が付いたら再開する |

### 実測

| 操作 | 変更前 | 変更後 |
| --- | ---: | ---: |
| `C:\git\VagWork\Vag` の全体走査（表示 241 項目、73,906 ディレクトリ） | 12.7〜13.7 秒 | 6.8 秒 |

| 5,000 行の表の描画（`viewer_tests`） | 全文字片を走査 | 2.7 ms / フレーム |
| 非 Markdown の通知ごとの属性取得 | 作成・削除・改名のたび | 削除・改名前の名前は 0 回、作成・改名後の名前はバースト中に登録あたり 1 回 |

`host_tests` の `TreeRescanEfficiencyChecks` に加えた検査: 3,000 件の兄弟行の追加と削除がタイマー分割で実行され（最大スライス 37〜40 ms、親は展開状態を保つ）、.md 入りフォルダを外から root へ移動（REMOVED + ADDED）すると表示される、走査中の再要求が完了後に1回だけ走る（世代番号が1つだけ進む）、同パス再登録後にそのファイルを開くと新しい行が選択される、監視 0 件で完了ポーリングが止まり監視が付くと再開する。`viewer_tests` はズームの往復で描画が画素一致すること、5,000 行の表のスクロールと検索を検査し、`diagram_tests` は部分的な可視矩形での描画が全体描画の該当領域と画素一致することを検査する。
