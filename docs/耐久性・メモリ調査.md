# MMViewer 耐久性・メモリ調査

初回調査日: 2026-09-05。初回の対象は x64 Release、配布exeの SHA-256 は `8D95EBBE27A11126E6FB3710299D850F7682F1425A71B4182AF13F68B023004D`。**初回調査では**製品コード・配布exeを変更せず、独立した診断用実行ファイルと一時設定で検証した。その後、修正の指示を受けて以下の対策と回帰試験を追加した。初回の実測値は比較用の履歴として残している。

## 今回の修正

| 対象 | 修正した処理 |
| --- | --- |
| 文字コード確認中のメモリ破損 | 確認画面を閉じた後にタブID・読込世代・キャンセル状態を再検証。配列要素への古い参照を使わず、追加・閉じる・切り替える操作で対象が変わった回答は適用しない |
| 100件を超えるタブの復元 | 設定内に実在する `Tab` セクションを列挙し、数値順に復元。保存件数の申告値だけを信用せず、後半のタブ・順番・選択・表示設定を読み戻す |
| 大量ファイル追加時の停止 | 追加処理をまとめ、タブ表示の再構築と選択文書の読込を一括追加の最後に実施。既存タブの重複判定にも索引を使用する |
| 消えたフォルダの展開履歴 | 既存のバックグラウンド走査中に展開候補の存在を確認し、正常な最新結果で消滅が確認できた履歴だけ削除。空の実在フォルダ、アクセス失敗・除外・再解析ポイントの未走査範囲、別登録フォルダの履歴は保持する |
| 親フォルダ再作成後の監視停止 | 失敗した監視を退役させ、3秒間隔の再試行でハンドルを再作成。再開時には現在の文書と関係するフォルダ一覧も確認し、復旧までの変更を取り込む |
| 差し替え画像の制限漏れ | 初回と再表示で同じパス・ファイルサイズ・寸法検証を実施。各辺16,384 px・4,000万画素・20 MiBの制限、寸法変更後の配置、失敗表示を更新する |

セッション保存は文字列をメモリ上でまとめ、一時ファイルへの書き込みが完了してから置き換える。終了時と明示的な保存ではディスクへのフラッシュも待つ。スクロール停止後の自動保存はフラッシュを省略し（[性能最適化](C:/git/MMviewer/docs/性能最適化.md)の2回目の項を参照）、書き込み途中の電源断は既存の `.bak` フォールバックで前回の完全な設定に戻る。以前の完全な設定をバックアップとして残し、書き込み失敗時に途中の設定を採用しない。自動保存に失敗した場合は状態を表示して10秒間隔で再試行する。終了時に保存できない場合は、再試行・保存せず終了・終了の取り消しを選択できる。確認中の再入による二重終了も防いでいる。[保存・復元・監視の実装](C:/git/MMviewer/src/native/main.cpp)

画像デコーダは描画準備中だけ保持し、元ファイルをロックし続けないようにした。大きな画像代替テキストの作業用バッファも解放し、小さいバッファは再利用する。[画像の実装](C:/git/MMviewer/src/native/viewer.cpp)

### 追加で再現したフォルダ一覧のハング

初回調査対象と同じ配布版を使ったPID 64712のハングを、実行中のスタック・ネイティブTreeView構造・同じオブジェクトから作成したMAPで照合した。停止経路は `AcceptTree` → `ReplaceFolderTree` → `UpdateRootTitle` → `TV_SetItem` → `TV_CalcScrollBars` → `TV_SmoothSetTopItem` → `TV_GetShownIndexItem` で、最後の関数が約7,842フレームを占めていた。[スタック](C:/git/MMviewer/artifacts/hang-64712/stacks.json) / [MAP](C:/git/MMviewer/artifacts/hang-64712/mapped-old.map)

同じ階層を独立したTreeViewへ再構築した対照試験では、旧順序はタイトル更新から戻らず、プロセスを25秒で打ち切った。タイトル更新の直前に `WM_SETREDRAW(TRUE)` を送る順序へ変えた試験では、その**単一のネイティブタイトル更新**が0.3066 msで戻った。この数値は本体のフォルダ交換全体の時間ではない。再計算後にサイドバーを非表示にする条件でも、同じ更新は0.2156 msで完了した。[旧順序](C:/git/MMviewer/artifacts/tree-native-result-64712.json) / [修正順序](C:/git/MMviewer/artifacts/tree-native-result-64712-fixed.json) / [非表示時](C:/git/MMviewer/artifacts/tree-native-result-64712-fixed-hidden.json)

## 初回調査の結論

**修正が必要な問題を6件確認した。最優先は文字コード確認中の解放済みメモリへの書き込み。** 通常の開閉反復では、回数に比例して使用中ヒープやGDI・USER・ハンドルが増える兆候は確認されなかった。ただし、消えたフォルダの展開履歴が無制限に残る問題は別に再現した。

| 優先度 | 問題 | 再現結果 |
| --- | --- | --- |
| P1 | 文字コード確認中のタブ追加によるメモリ破損 | AddressSanitizerが `main.cpp:499` の解放済み領域への1バイト書き込みを検出 |
| P1 | 101個目以降のタブを再起動で復元しない | 256タブを保存しても100タブだけ復元。選択位置も255から99へ変化 |
| P1 | 大量追加がUIスレッドを長時間占有 | 100タブから156文書追加する処理が12,078 ms。小さなMarkdownでも発生 |
| P2 | 消えたフォルダの展開履歴が蓄積 | 現在の一覧は3項目のまま、1,500回の入れ替えで履歴1,501件。保存は391 ms |
| P2 | 親フォルダ再作成後に自動更新が復旧しない | 単独ファイルの親を削除・再作成後、監視が未開始のまま残り、次の保存を検出しない |
| P2 | 画像差し替え後の再表示で寸法上限を再検証しない | 幅20,000pxの画像が、再表示では描画され、新規解析では拒否された |

P1はクラッシュ・状態喪失・大きな応答停止につながる問題、P2は条件付きの機能不全・資源増加として整理した。

## 初回に再現した問題と当時の修正方針

以下の実装説明・行番号・数値は修正前の診断対象を指す。現在の対策は冒頭の「今回の修正」に記載した。

### 1. 文字コード確認中の解放済みメモリ書き込み

`AcceptLoad` は `Tab& t` を取得したまま `MessageBoxW` を表示する。確認中の別起動による `WM_COPYDATA` などで `OpenPaths` が実行されると、タブ配列が再確保される。確認後も古い参照を使用するため、`t.cp932=true` が解放済み領域を書き換える。「いいえ」の後の `t.status` も同じ参照を使う。

CP932文書の確認中に40タブを追加する独立プロセスで再現。元タブへのCP932設定が失われ、AddressSanitizerは実際の `heap-use-after-free` を検出して停止した。メモリリークとは別の、メモリ破損の問題。

修正方針: 確認後にタブID・読込世代・キャンセル状態を再確認し、有効なタブを再検索する。モーダル処理をまたいでvector要素への参照を保持しない。[実装](C:/git/MMviewer/src/native/main.cpp) / [ASanログ](C:/git/MMviewer/artifacts/endurance-audit/encoding-asan.log)

### 2. タブ復元が100件で打ち切られる

保存側は全タブを記録する一方、`Restore` は `std::min(100, ...)` で読み込み件数を制限する。256件の保存データから100件だけ復元されることを、実際の `App::Restore` で確認した。診断内で既知フォルダAPIの戻り先を一時フォルダへ差し替え、実ユーザーの設定には触れていない。

修正方針: 開ける件数と保存・復元できる件数を一致させる。上限が必要なら明示し、保存済みの後半を無言で落とさない。[実装](C:/git/MMviewer/src/native/main.cpp) / [実測](C:/git/MMviewer/artifacts/lifetime-probe/run-39888-46543843/results.jsonl)

### 3. 大量ファイル追加で応答が止まる

`OpenPaths` はファイルごとに全タブを削除・再挿入する `RebuildTabs` と、最終的に取り消される読込開始を繰り返す。UIスレッドの一つの処理内で行うため、件数増加で待ち時間が急増する。

| 追加前 → 追加後 | 追加件数 | `OpenPaths` のUI占有時間 | 保存のUI占有時間 |
| --- | ---: | ---: | ---: |
| 0 → 32 | 32 | 172 ms | 47 ms |
| 32 → 100 | 68 | 1,484 ms | 110 ms |
| 100 → 256 | 156 | 12,078 ms | 265 ms |

文書は短いMarkdownであり、大きな本文の解析時間ではない。時間はこのPCの1回の実測で、別の負荷や環境により変わる。

修正方針: 一括追加の状態更新をまとめ、タブ表示の再構築と最終選択文書の読込を必要な回数に減らす。大量追加を分割できるようにする。[実装](C:/git/MMviewer/src/native/main.cpp)

### 4. 消えたフォルダの展開履歴が残り続ける

`expanded` は展開時に追加されるが、通常の再走査で消えたフォルダの情報が整理されない。ユーザーが「リストから削除」を操作した場合とは処理が異なる。

1つの子フォルダを別名へ入れ替え、展開する操作を1,500回繰り返した。現在のTreeViewは3項目のまま、保持履歴は1,501件になった。この履歴は設定にも書かれ、保存時間は391 msに達した。これはポインタの解放忘れではなく、**不要な状態を無制限に保持する問題**。

修正方針: 正常に走査完了したフォルダ内で、存在しなくなった展開履歴を整理する。一時的なアクセス失敗や未完了の走査では既存設定を消さない。[実装](C:/git/MMviewer/src/native/main.cpp) / [実測](C:/git/MMviewer/artifacts/lifetime-probe/run-39888-46543843/results.jsonl)

### 5. 親フォルダ再作成後の自動更新停止

単独で開いたMarkdownの親フォルダが削除されると、監視完了と再登録にエラーが返る。`PollWatches` は `Arm()` 失敗を処理せず、その監視が残る。同名フォルダを再作成しても、フォルダ一覧へ登録していないケースでは定期走査による回復もない。

再作成した文書を再アクティブ時の確認で読み直すことはできたが、その後の保存を検出しないことをHost全体で確認した。

修正方針: 監視失敗を状態として扱い、ハンドルを作り直す再試行とフォールバックを用意する。[実装](C:/git/MMviewer/src/native/main.cpp) / [再現ログ](C:/git/MMviewer/artifacts/endurance-audit/watch-recreate.log)

### 6. 画像差し替え後の寸法制限漏れ

初回画像読込は最大幅・高さ16,384pxなどを確認するが、画面外へ出て表示用ラスタを解放した後の再読込は、古い `imageValid` と寸法をそのまま使う。画像ファイルが置き換わると再検証を経由しない。

100×100の赤いPNGを表示して画面外へスクロールし、同じパスを20,000×1の緑PNG（215バイト、展開後約80KB）へ置換した。再表示では緑が1,570画素描かれ、新規解析では0画素で拒否された。寸法制限が再読込では適用されないことを、小さなメモリ使用で確認した。

修正方針: 初回と再読込で同じ検証を実施し、変更された画像の寸法・失敗状態を更新する。[実装](C:/git/MMviewer/src/native/viewer.cpp) / [測定値](C:/git/MMviewer/artifacts/endurance-audit/image-lifecycle/result.json)

## 初回の静的確認と今回の対応

- `PollWatches` は非Markdownの作成・削除・名前変更通知でも、UIスレッド上でフォルダ一覧全体を走査していた。大きな開発フォルダを登録したままビルド成果物が大量に変化するケースは追加の応答負荷候補としていたが、その後の2回目の最適化で、既知フォルダの集合による判定、変更のあった登録フォルダだけの再走査、同一結果でのTreeView再構築の省略、監視バッファの64 KiB化に置き換えた。詳細と実測は[性能最適化](C:/git/MMviewer/docs/性能最適化.md)を参照。その後の3回目の最適化で、走査結果の反映自体を全削除・全挿入から差分・分割適用に変え、1件の .md 追加で10秒以上止まっていた状態を数 ms にした。
- 初回は、描画側の `imageAlternate` が `clear()` 後も過去最大の容量を保持し、文書キャッシュの容量計算にも含まれなかった。反復回数に比例するリークとは区別したが、今回、8,192文字分を超える作業用バッファを解放する処理を追加した。初回調査では巨大altの実測はしていない。
